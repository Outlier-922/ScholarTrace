# 明确的完成标准与收尾顺序

适用当前0.25.0。依据为用户提供的赛题文字中的“详细命题模块”“测试数据集与验证用例”和“作品提交要求”，不额外提高为满分标准。整体状态由evaluation/acceptance.json记录，不能按版本号、阶段数或自动测试数量计算完成百分比。

## 什么程度才算完成

| 关口 | 通过条件 | 当前情况 |
|---|---|---|
| 必要功能 | 六个模块及Agent流程都有符合赛题的实际操作链路，必要能力缺失项已补齐 | 六模块已有入口；版本语义、复杂解析、检索/生成质量、翻译交互、发现筛选、综述/方向、写作及规划仍有部分实现项 |
| 官方用例与科研质量 | v7后上传v1的内容/版本提示、扫描PDF、541页长书实测可复查；代表性问答/对比/翻译/图谱/写作按原文或数据核对 | 已有分阶段记录，仍需集中关闭缺口；有出处和代码测试通过不能代替答案正确 |
| 可交付材料 | 评审可访问GitHub/Gitee源码及历史；最终版本技术PDF不超过30页；普通话MP4为5—8分钟、至少1080p；README参赛者信息完整 | 本地Git已有；PDF仍为旧版草稿，视频未成片，仓库访问未核验，身份按用户要求暂留空 |
| 外网使用与一致性 | 有评审期间可用的公网演示地址；需要登录时提供专用账号；源码、文档、视频和线上功能对应同一最终版本 | 尚无公网入口，部署和最终一致性核验待做 |

四个关口会复用同一批功能证据，不能把它们相加当分数。验收针对赛题列出的能力与样例，允许明确标注适用范围；不能用“将来所有论文、所有问题都100%正确”作为无限延长开发的条件，也不能把缺失的必要能力改名成边界而当作完成。

“可以在本机演示”“材料齐全可提交”“赛题能力完整且已验收”是不同状态。当前属于本机可运行、尚有必要缺口的功能原型，不能称为完整参赛成品。有缺口提交应如实披露，不能伪称全项通过。

## 固定的收尾工作包

以下是现有要求的收尾，不再追加赛题之外的功能。每包以真实结果关闭；失败保留，不靠增加文档或测试数量关闭。

| 顺序 | 工作包 | 关闭时要看到的结果 |
|---|---|---|
| 1 | 官方基础场景 | 版本用例、扫描件、长书的实际输入版本、操作、输出和资源记录；长书验证冷索引、跨进程缓存、逐页加载与锚点 |
| 2 | 必要能力补齐与科研输出核对 | 对照总验收表逐项处理剩余部分实现；重点是Agent意图流程、解析、单/多文问答、翻译、发现、图谱/方向与写作。现有已通过范围不反复扩充无关测试 |
| 3 | 集中演练和材料 | 用一次连贯的“导入→问答/阅读→发现/图谱→写作/绘图”演练验证；按真实最终功能制作≤30页PDF及5—8分钟普通话1080p MP4；核验环境模板、安装说明与源代码历史 |
| 4 | 评审访问与最终冻结 | 配置实际托管/公网入口，核验外网操作与账号，填写实际参赛者信息；确认仓库、PDF、视频及线上版本一致，再做正式提交准备 |

已完成工作包1中541页长书按所列范围的工程验收：首次冷索引超时保留，恢复后全量缓存与跨进程读取通过，见[实际记录](STAGE22_TEST_REPORT.md)。现处于工作包2：0.19.0已接通有界反馈、计划版本与本地替代，见[Agent实际记录](STAGE23_TEST_REPORT.md)；0.20.0已接通指定段落翻译、预算与缓存，见[翻译实际记录](STAGE24_TEST_REPORT.md)。0.21.0进一步接通明确条件书目发现、独立请求预算、缓存恢复和核对快照交接，见[发现实际记录](STAGE25_TEST_REPORT.md)。0.22.0进一步接通固定CSV规则、绘图预算恢复与复现包，见[绘图实际记录](STAGE26_TEST_REPORT.md)。0.23.0接通单篇明确确认后的全文交接与确切版本后续任务，见[交接实际记录](STAGE27_TEST_REPORT.md)。0.24.0接通全文分批、预算、缓存、原页对照与编排等待/恢复，实测发现语义误译并另存校订，见[全文实际记录](STAGE28_TEST_REPORT.md)。自动批量下钻/下载编排、全文对齐/译文质量、完整意图和科研输出仍未验收。继续统一核对能力并只补必要缺项，再制作最终材料。

当前机器清单仍有**14项必要能力部分实现/待验收、5项交付未齐**。这些不等于19个全新模块，也不能换算成完成百分比；具体条目与证据见[总验收表](ACCEPTANCE.md)。当前0.24.2进一步关闭RoBERTa最终配置的已知检索缺失，见[实测对照](STAGE30_TEST_REPORT.md)；此前0.24.1修复问答数字漏检与比例表示误拒绝，并加入保存候选的本地复核，见[具体结果](STAGE29_TEST_REPORT.md)；0.24.0已接通全文计划与编排等待；单纯补验收记录不再为了阶段数升级版本，只有实际产品变更才创建新的代码快照。

## 不擅自加码的事项

- 赛题要求公网地址，**没有要求必须购买独立域名或自有云服务器**。实际托管方式和费用在可审阅的部署方案准备好后再确定。
- 独立人工评审、完整异机恢复、生产多租户隔离是有价值的工程建议，不能混写成赛题额外必交材料。科研输出本身仍应按原文核对；多用户推荐拓展与生产数据隔离也不是同一件事。
- 不强制某一种Agent框架或绘图工具；按规则验证任务规划、工具执行与实际业务闭环。
- 真实账号登录、评审访问授权、报名身份和正式发布信息需要本人参与。当前不会编造姓名、学校、团队、复核人或公网地址，也不会把密钥写进文档。
- 赛题文字要求以实际报名身份参赛。README中的“团队信息”按报名主体填写；此前用户要求暂不填写，继续保留到交付前。

## 如何确认已结束

打开[总验收表](ACCEPTANCE.md)，逐项查证据，再运行：

~~~powershell
.venv312/Scripts/python.exe -X utf8 scripts/check_acceptance.py --require-ready
~~~

该命令只检查记录状态和证据文件，不自动判断学术事实、视频内容或公网可用性。只有实际验收与材料/外网条件均满足，再把对应必要项改为通过；所有必要项通过、人工确认交付一致后，才称整体完成。当前命令返回未就绪属于如实报告。
